Adding real recordings to wake-word training

Trstenko project — tools/wakeword/. This is "Step B": the thing that actually moves the model past "works on synthetic voices" toward "works on a real person in a real room." Pairs with TRAINING_GUIDE.md, which covers what the training numbers mean.

Why this step exists. The model trained so far only ever heard synthetic text-to-speech voices and computer-generated noise. It scores perfectly against more of the same — that doesn't tell you whether it recognizes an actual human voice through an actual microphone. This step adds the one kind of data that answers that question.

Step 1 — record the wake word

Get a handful of people (the more voices, the better it generalizes) to say "Trstenko" out loud, several times each. A phone voice recorder is fine for a first pass — it doesn't need to be the final hardware.

  • How many: 20–50 recordings is a useful start. More is better, but even 20 real ones outweigh a lot of extra synthetic ones.
  • Variety helps: different distances from the mic, different tones (flat, questioning, in a hurry), a few with background noise, a few with silence.
  • One utterance per file — each recording should be just the one word, trimmed roughly to its length (a second or two of extra silence around it is fine, it doesn't need to be exact).
  • Format: any common audio format works, but 16kHz mono WAV is the target the rest of the pipeline uses — if you're not sure, don't worry about converting by hand, just save what your recorder gives you and flag it if training complains.

Save every file into:

tools/wakeword/data/positive_real/

Step 2 — record the room

Record 30–60 minutes of whatever the device will actually sit next to — normal conversation, TV, kitchen sounds, silence, footsteps. This is what teaches the model what "not the wake word" sounds like in the real world, instead of only computer-generated noise.

  • Doesn't need to be one continuous file — several shorter recordings covering different times of day/activities are fine.
  • The point is variety of realistic background, not perfect audio quality.

Save it into:

tools/wakeword/data/negative_real/

Step 3 — turn the new data on

Open tools/wakeword/config/training_parameters.yaml. Near the bottom of the features: list are two blocks that start with # (commented out) mentioning positive_real and negative_real. Remove the # at the start of each line in both blocks. That's the only file you need to edit by hand.

Before:

  # - features_dir: data/features/positive_real
  #   sampling_weight: 5.0
  #   penalty_weight: 1.0
  #   truth: true
  #   truncation_strategy: truncate_start
  #   type: mmap

After (just the #s removed):

  - features_dir: data/features/positive_real
    sampling_weight: 5.0
    penalty_weight: 1.0
    truth: true
    truncation_strategy: truncate_start
    type: mmap

Step 4 — rebuild and retrain

Using the dashboard (python -m tools.wakeword.ui, then http://127.0.0.1:5151):

  1. Click Build features — do not click the three "Generate…" buttons above it, your real recordings are already audio, they don't need synthesizing.
  2. Wait for the log to go quiet and the button to re-enable.
  3. Click Train (the default numbers are fine to start with).
  4. Wait — this is the slow step, expect several minutes.

Or from a terminal, in tools/wakeword/:

docker compose run --rm train python scripts/build_features.py
docker compose run --rm train bash scripts/train.sh

Step 5 — check the result and export

Look at the new row in the dashboard's Run history table (or data/runs/<newest>/summary.json):

ColumnWhat it means
Ambient measuredShould say "yes" — if it says "nan", something's wrong, see TRAINING_GUIDE.md.
frrHow often it misses the real word. Lower is better.
faphFalse alarms per hour on real background audio. Lower is better, aim for ≤2.
Recommended cutoffThe number to copy into the Export box next.

Type that cutoff into the probability_cutoff box next to the Export button and click it. That copies the finished model into firmware/wakeword/models/ — the actual file the device loads.

What "good" looks like here is different from the synthetic runs. A synthetic-only run hitting frr=0/faph=0 was almost too easy. With real voices and real room noise in the mix, don't expect a perfect score on the first try — some frr and some faph is normal and informative. If faph is high, add more real room recordings covering whatever triggered it. If frr is high, add more real voice recordings.

Checklist

  • Recorded 20+ people/takes saying "Trstenko" → data/positive_real/
  • Recorded 30-60 min of real room ambience → data/negative_real/
  • Uncommented both blocks in training_parameters.yaml
  • Ran Build features
  • Ran Train
  • Checked the new Run history row — ambient measured = yes
  • Exported at the recommended cutoff
